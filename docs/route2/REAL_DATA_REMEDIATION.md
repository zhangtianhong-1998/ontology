# 路线 2：真实数据运行后的整改设计

本设计针对用户在数据机上运行路线 2 的反馈。我们拿不到实际 CSV、YAML、运行配置和完整 trace，因此不把运行摘要当作独立复现，也不以对象数、属性数或通过率证明本体语义正确。所有例子只解释算法，不预设用户库中存在对应表或字段。

## 1. 事实、推断与待核验项

## 2. 构建流程与配置要求

按以下顺序处理，结果均落盘并标明输入快照与未处理范围：

1. **数据与列画像。** 导入现有 YAML 元数据、CSV 与约束，计算全输入的空值、可用值、形态和有界样本。画像只证明本次导入范围；如果 CSV 是样本，全空不等于数据库中永久全空。
2. **列角色分流。** 为每列生成 `empty_in_input`、`audit_time`、`technical_identifier`、`reference_key`、`semantic_name`、`definition`、`formula`、`scope` 或 `unknown` 等候选角色，并记录判据与置信边界。全空列不进入语义提示词，保留源元数据、统计与来源映射；审计时间和明确的技术主键由程序绑定为数据属性，不让 LLM 重复判断。业务日期、度量编码、非主键 ID 和含义不明的列不能按名称直接丢弃。角色允许多值，例如业务编码既是标识，也可能是跨表关联键。
3. **定义记录识别与概念候选。** 从有名称、定义、口径、公式、单位、范围等证据的记录中抽取定义记录；按类型相容性、显式编码、名称/别名和文本相似性形成候选簇。模型只对有证据的簇判断共用概念、从属或不同概念，并保留原始记录、作用域和反例。物理表、记录对象与业务概念分别存储，不因一张表存在就新建一个同名本体类。
4. **跨表规则发现与验证。** 先多通道召回，再对可描述为规则的候选做全输入验证，最后才让 LLM 判断业务关系含义，程序编译并复验关系计划。没有验证的候选保留为未决，不转成外键或本体关系。
5. **联合行包与增量构建。** 对通过技术验证的关联规则，定向选取少量跨表记录及反例，结合相关定义与现有本体邻域组包；LLM 生成结构化 delta，Judge 和程序验证后原子合并。百万行只由 SQL/索引扫描，LLM 调用按候选语义组计费，不逐行调用。
6. **实例执行和浏览。** 用最终规则处理记录，输出对象、字面属性、关系、规则、未决与覆盖率；本地页面只加载有界预览，完整结果留在磁盘。

企业文档是可选输入。`mcp.enabled: false` 时，构建提示词明确声明知识检索关闭，只使用数据库元数据、记录与已核验候选；不生成“缺少知识”的假错误，也不把无 claim 解读为“没有关系”。开启但返回空、无关、超时、服务错误时分别记录状态，并继续使用可用的数据库证据。有效 claim 只能作带出处的补充，不能替代数据关联验证。

## 3. 定义记录如何形成概念

例如两条记录分别叫“阿里云收入”和“商业市场收入”，共有“收入”一词只能召回“收入”度量候选，不能直接合并。要同时检查定义、计算口径、单位、业务范围和上下游引用：它们可能是同一概念的不同限定，也可能是两个不同度量。输出至少区分：`source_record`（原记录）、`concept_candidate`（待归纳的含义）、`scope/qualifier`（适用条件）、`decision`（同一/派生/相关/未决）及证据 ID。输入缺少定义或口径时，应保留未决，不由名称臆造计算关系。

概念候选的召回可用名称标准化、别名表、BM25/向量和公式词项；归并必须考虑单位、口径与冲突证据。按簇调用 LLM，缓存同一语义组的判定。报告簇数、所覆盖定义记录数、未聚类数和未决数，不把覆盖率误写成语义准确率。

## 4. 关联规则的多通道发现

发现对象是有方向的字段或字段组，以及适用条件，不是简单的“两个列很像”。至少设计以下通道，并保留各通道来源：

| 通道 | 候选产生 | 验证重点 |
| --- | --- | --- |
| 精确标识 | 约束、列注释、相同原值、结构化引用字段。 | 非空覆盖、目标唯一率、重复目标、缺失目标；防止两个自增 ID 偶然重叠。 |
| 名称与别名 | 名称/说明字段倒排、BM25/向量；显式同义词表或记录中的标准名—别名对。 | 别名规则的来源、作用域、歧义率；名称近似只用于召回。 |
| 规范化 | 限定的大小写、空白、标点、前后缀或编码变换候选。 | 原值与变换值同时保存；验证碰撞、新增匹配与误配，未经证明不全局启用。 |
| 条件与多态引用 | 类型/来源字段控制目标表或目标列、JSON 路径、枚举值。 | 每个条件分支分别验证；条件外记录不能当正例。 |
| 复合键与范围 | 编码加业务域、版本、命名空间或有效期的字段组。 | 条件内外覆盖及唯一性；同一编码在不同范围可能指向不同对象。 |

候选排序应兼顾不同源表、通道和业务角色，不让前几个大表或通用 `id` 消耗全部核验预算。`max_candidate_validations` 是计算预算，不应单独用“12 调到 50”作为质量修复。每个候选记录原值/变换、selector、scope、匹配数、唯一/多义/缺失数、条件外匹配数、反例和输入范围。只把满足可配置门槛且无关键冲突的规则交给下一阶段；门槛数值应在合成对照与真实运行报告中校准，不在代码里伪装成业务真值。

## 5. 跨表行包：哪些行放在一起

以一条**已核验的候选规则**为组包单位，而不是随机取各表前 3 行。程序按照该规则在导入快照中选取：至多若干个唯一匹配的正例、一个无目标或多义反例、一个条件外例子；如存在不同作用域，再覆盖不同分支。每个例子包含双方稳定记录 ID、匹配字段原值、必要的名称/定义/口径/单位/范围字段、规则和验证计数，以及对应的元数据证据 ID。长文本按字段设限，但保留原文路径和截断标记；整个包有明确字节预算，超限时减少例子或拆成多个独立包，不悄悄截掉条件与反证。

LLM 读取行包后只回答三件事：这是否是业务关系、应归到哪个用户定义的根关系或其派生、适用条件是什么。输出结构化 `RelationPlan` 候选，引用包内证据；无法确定则返回未决。程序随后核对字段存在、条件可执行、变换受支持、源/目标身份唯一以及证据完整，再编译计划。一个字段规则可能有多个业务语义，反过来同一关系类型也可由多条记录规则支撑；二者不能混写。

## 6. 上下文、预算、失败与质量门槛

- `current_core` 只传根类型、相关类型定义、少量已接受邻居和映射摘要；完整 core 留本地校验。当前单位只传语义列及确定性绑定的简表，不传全库所有列和整行宽表。每个 LLM 请求记录组件字节数、输入预算、服务端 token、耗时及阶段。提高超时仅作服务端慢响应的补救，不代替缩小上下文；对完全相同的请求超时，不把 5 次语义修复机会耗在重复等待上。
- 记录级提取的全量成本用 SQL 扫描、索引与批处理衡量；语义调用预算按定义簇、候选规则、审查及检索分别统计。每阶段输出 `attempted/checked/accepted/unresolved/skipped` 与原因；预算耗尽仍保留未处理范围。
- 评估分开报告工程完整性、候选召回、匹配规则精度和本体语义质量。至少用合成数据覆盖全空列、技术时间、业务日期、别名、复合键、多态条件、重复目标、缺失目标、同词异义和无关系场景。真实业务语义没有人工 Gold 或独立审查时标记 `unjudged`，不能因 Judge 通过而宣称正确。

## 7. 页面要求与本轮边界

页面的类型卡直接显示 ID、定义、父类型和证据；实例卡显示来源、业务编号、时间、描述等已有字面属性，并注明属性预览上限。真实数据示例每表预先物化前 3 条记录，0 条实例关系时仍可浏览有限的记录属性；这不是代表性采样。页面不能为了显示详情而一次载入百万条断言，所有源文本用文本节点渲染。

本轮已有以下**原型改动**：列角色与提示词分流、缩小表/core 上下文、有限的原值相等联合行例、定义记录与别名的有界候选召回、企业检索空正文拒收和知识关闭提示、相同请求超时停止重复语义修复、结果页有界属性预览。定义记录候选连同原记录片段进入增量提示词；别名候选只落盘为诊断结果，不作为关系计划。两种候选都有采样覆盖报告。真实数据示例设定了比模块上限更小的抽样预算。这些能力仍需真实数据机验证。**尚未实现**定义记录到业务概念的稳定归纳、多通道别名/变换/复合条件的全输入规则验证，以及从联合行包自动生成并复验跨表关系计划。现有联合行例仅说明原值相等候选，不能宣称已解决隐藏业务关联。

代码要求保持简洁：每个阶段使用小而清晰的数据契约与可审计产物，优先复用现有 DuckDB/SQLite、YAML 和 AgentScope 边界；不要以一个大型 Agent 替代确定性的统计、连接和校验。
