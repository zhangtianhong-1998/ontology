# 路线 2：重置、改造与合成实验

本轮先清空 `route2/runs/` 中 28 个旧实验目录，再从提交 `03a8000e` 的独立工作树建立基线。输入 `route2/local_data/` 没有删除。基线与清理范围见[实验重置记录](EXPERIMENT_RESET_20260925.md)。下面的水果数据均由脚本生成；仓库没有用户真实数据。火山引擎 `deepseek-v4-flash` 分别在 6 行受控数据和 23 表小样本上做了在线抽取。

## 为什么旧结果失效

旧逐表路径让模型主要从表注释和当前 core 提出类型、关系。随着 core 增大，用户数据机报告单次请求达到约 27 万 token，5 张表超时；而大多数跨表候选在 12 次验证上限之外。表到类型的直接映射又把物理表当成业务概念的主要来源，最终出现大量属性、零条关系。这里的“5 张表超时”“零条关系”来自用户提供的数据机报告，仓库没有真实数据，未作独立复现。

技术连接和业务关系此前混在一起：字段值相等既不足以证明两个定义是同一概念，也不足以证明一个指标计算依赖某度量。反过来，即使一个记录包证明一对记录有业务关系，也不能把这个结论外推到该字段规则连接的所有行。旧页面默认展开整张元数据图，源字段和约束边数量远大于业务边，因而难以检查真正想看的关系。这些原因分别对应下面的候选核验、概念/关系证据门禁、见证记录限制，以及页面局部展示。

## 改了什么

1. **先找可复核的连接。** `discovery.py` 可对合格的标识、编码、名称和引用列读取完整 distinct 值，按实际出现的 `business_type/source_type` 值提出条件候选。选中的字段对仍由程序对完整输入做 JOIN，分别计入唯一命中、缺目标、多义、缺作用域和条件外记录。技术规则写进 `association_rules.yaml`；已核验与部分命中的字段边也写进 `meta_graph.yaml`，状态为 `inferred_technical_match`，不冒充声明外键或业务关系。适用范围见[关联核验说明](ASSOCIATION_VERIFICATION.md)。
2. **把源行形状和业务概念分开。** 每张表产生一个 `source_record_type`，保留表及全部列映射。概念包必须有未截断的定义记录、逐字引文和明确的适用范围，才可编译 `business_type`。一个地区或期间若是观测坐标，不能写进类型身份。关系包须引用已完整核验的技术规则和同一正例两端的业务文本；公式依赖还要求源公式点名目标。执行计划只物化被引证的正例记录对；同一正例两端都精确对齐到业务类型时，才另生成业务类型关系。关系端点的物理类型由程序绑定，不再让模型猜测。接受的关系仍标明其语义依据来自样例。
3. **新配置先做程序分析，再做组包抽取。** `runtime.real.example.yaml` 和水果配置使用 `incremental.mode: source_mapping_only`。逐表阶段不再给 LLM 发送全部表上下文；可选关联 Agent 和选中的概念/关系包才会调用模型。旧 `table_semantic` 模式仍供原有测试使用。企业 MCP 和外部本体目前只接在旧逐表模式；开启它们时新模式会直接报配置错误，避免默默跳过检索。
4. **页面按需要展开。** 标准 `build` 收尾自动生成 `viewer.html`。元数据页默认显示表清单；点选表后展示该表字段、来源、约束及局部技术连接。业务派生类型与源记录类型分开显示，源类型较多时改用可搜索清单。页面仍分别显示候选、已核验技术连接和业务关系。

最终小样本元数据图有 32 条推断技术边，百万行有 30 条；两者的声明外键仍是 0。完整构建的 `status=partial` 是真实状态：小样本还有 1,481 对候选未核验，百万行还有 1,472 对；百万行只给 9,857 张去重/限额语义卡建索引，且示例配置将 `max_llm_bundles` 设为 0。零次模型调用用于测本地扫描与组包成本，不代表“自动抽取出了完整本体”。本机耗时不推断 Windows 数据机耗时。早一轮同样输入的逐表 mock 构建曾发出 44 次录制响应调用；这不是实际模型 token 或费用。

在线实验先暴露了两个实际故障：模型将空对象输出成字符串 `"{}"`，以及关系组包名额被“同一概念定义键”占用。现在只解码合法的 JSON 对象，并让被跳过的对齐线索不消耗关系包名额，同时优先选明确引用键。随后模型把根类型 `Metric/Measure` 错填为可执行关系端点；端点现由源映射确定，模型只判断关系含义。6 行在线产物在 `runs/fruit-controlled-live-v4-20260925/`；实验期间使用忽略目录配置和本机临时凭据副本，结束后已删除副本。6 行手工合成输入有已知预期，可检查链路是否产生目标关系，但没有独立业务 Gold，不能推断真实数据上的语义精度。

23 表在线产物在 `runs/fruit-smoke-live-8k-20260925/`。此前 2,048 输出 token 上限的对照运行出现 2 次服务端 `finish_reason=length`；用正式示例的 8,192 上限重跑后为 0，但耗时约 203 秒，仍有 8 个包未接受。未接受的主要原因是作用域/单位不一致、引文不在同一正例、模型判定无法确定或程序/Judge 拒绝；不是靠加 token 就能消除。唯一接受的记录关系是看板卡片指向指标详情，其两端记录没有同时精确对齐到已接受的业务类型，因此程序没有把它提升成业务类型关系。两次模型输出还具有随机差异，不能把结果差异全部归因于 token 上限。

13 行运行首次发现数值列注释含“水果”时同时被识别为维度列，导致数值候选消失。已改为数值角色优先，再跑程序探针得到 4 个候选。定义包模型有时遗漏 exact 代表记录，现仅在编译器明确拒绝时附错误反馈重试一次，仍须重新校验；13 行在线运行的 7 个接受包中有 3 个经过这种修复。事实绑定故意拒绝同名双类型，不会任选其中一个。此处的瓶颈是跨定义表的类型等价证明，而非把同名类型当一个类型的宽松规则。
