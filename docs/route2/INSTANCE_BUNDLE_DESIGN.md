# 路线 2：百万记录下的实例检索与增量组包

状态：设计方案，尚未实现。输入仍是离线 YAML 元数据和 CSV；本文不假定真实数据中有任何特定对象、字段或关联。目标电脑不支持 Docker，检索和模型计算都应能在本机运行。

## 1. 要解决的问题

当前程序按表生成本体增量。每表最多带入 3 个已核验字段对；每对默认只取 1 组原值相等的跨表记录和 1 条反例。定义记录候选来自有界名称抽样，别名候选只落盘。现有 embedding 用于外部本体、MCP 命中重排和已接受表的上下文召回，**没有用于 CSV 实例组包**。这使大量仅在具体记录中出现的定义差异、局部关联和长尾用法进不了模型。详见[当前实现状态](STATUS.md)。

百万行可以由数据库扫描，却不能逐行请求 LLM。输入可能大部分是配置、引用和定义记录；若每条定义都不同，唯一语义组数也可能接近记录数。设计须同时报告程序扫描了多少记录、召回了多少候选、哪些语义组进入 LLM，以及哪些仍未处理，不能把“扫描完 CSV”写成“完成本体抽取”。

推荐的处理链是：`全输入画像 → 列角色与语义卡 → 规则候选及检索候选 → 规则全量验证 → 两类证据包 → 组级 LLM 增量 → 程序复验与合并`。其中扫描、索引、连接和选例在本地完成，Agent 只探索少量难以用固定规则提出的关联模式。

## 2. 需求分解

| 编号 | 要求 | 验收方式 |
| --- | --- | --- |

## 3. 两种工作单元

**关联规则单元**以候选字段组或已验证的记录匹配规则为中心。它回答“哪些行按什么条件连在一起”。程序先从元数据、值域、结构引用、名称/别名中给出线索；专门的 ReAct 子 Agent 可以查询样本、匹配计数与反例，最多进行有界的改写和验证。Agent 输出受限 YAML：源/目标字段、允许的转换、selector、作用域、预期基数及证据。程序编译受支持的操作，并在本次导入的完整输入上重新计算。Agent 不提交自由 SQL，也不直接认定本体关系类型。

Agent 每次只处理一组有理由比较的字段或表，不浏览整库。工具限于 `describe_columns`、`sample_values`、`test_match`、`show_counterexamples` 这类有预算的只读操作；调用次数、返回行数、字段投影、SQL 耗时、临时磁盘和总验证候选数均受程序限制并记账。输出规则若不能编译为受支持的 JOIN、变换和条件，就保存为 `unresolved`，不能因为模型解释通顺便复用。不得把行 ID 列表或在样本上临时拟合的选择器伪装成一般规则；作用域或 selector 需要列含义、显式规则或独立留出分支的支持。全输入计数说明本次匹配范围，并不单独证明可跨概念族复用；缺少留出支持的局部模式标为 `observed_subset`。可执行规则的 YAML 与原始候选、验证结果分开保存；复用时仍按新快照重算命中和歧义。

Agent 的规则草案和程序的核验结果分开落盘，避免把模型声称的匹配率当成扫描结果。受限输出至少应有以下字段；首版只编译单列和有限变换，复合键与多态目标在后续扩展：

```yaml
rule_id: "<由规范化规则内容生成>"
source: {table: "<源表>", fields: ["<源字段>"]}
target: {table: "<目标表>", fields: ["<目标字段>"]}
transform: identity                 # 或已登记、可逆性已说明的有限变换
selector: null                      # 已支持的 Condition DSL，不接收 SQL 文本
scope_bindings: {}                  # 目标范围字段 -> 源范围字段
expected_cardinality: zero_or_one  # 仅为待核验假设
evidence_ids: ["<列说明或记录证据ID>"]
status: proposed
```

程序另写 `validation`：快照 ID、扫描行数、条件内外分母、唯一/多义/缺失数、碰撞、反例、留出分支和预算状态。`checked_technical` 只说明规则在本次输入可执行且统计明确；业务关系类型仍交给后续语义包判定。

**概念归纳单元**以定义记录为中心。名称、别名、说明、公式、口径、单位和适用范围组成检索卡。共词或向量相似只说明值得比较；例如两条名称含有“收入”的记录，可能是同一度量的不同限定，也可能计算口径不同。此单元应同时带入相近定义和冲突定义，由 LLM 判断是否有共同概念、派生关系或仍未决。物理表和记录身份继续保留。

同一关联规则可能匹配许多记录，先按条件分支、目标类型、单位、口径和范围分组，再各取少量例子。概念组不靠相似边的传递闭包：A 像 B、B 像 C，不能自动把 A 与 C 合并。高频通用词和公共编号也不能把一个包扩成整张表。

## 4. 从全量记录到有限候选

1. **全输入画像与卡片。** DuckDB 扫描全部导入记录，按列角色找名称、定义、公式、别名和范围字段。定义类记录形成语义卡；只有编码、条件或枚举的记录形成轻量引用卡，不强行送 embedding。`unknown` 列及 JSON 内的短文本须经有界形态探测和分层抽样；疑似定义但无法解释字段角色时进入待查卡，不直接丢弃。每张卡保存原值、字段出处、记录 ID、表角色、单位、版本、作用域和快照 ID。字段缺失写 `unknown`。仅在相关语义字段及范围都相同时去重，出现次数和各行 ID 留在磁盘，不把不同范围的定义压成一张卡。报告各表入卡、待查和未入卡数量及原因。
2. **硬条件先筛。** 显式编码、已验证关联规则、角色、命名空间、业务域和版本先限定主要比较池；已知单位或口径冲突另作对照池，不误当正例。缺少范围信息不当作相容证据；宽松回退须单列报告。精确键和已验证规则的命中目标不受语义检索 top-k 截断，但大量命中仍须分组取例。
3. **词法与向量补召回。** 在兼容集合内，对名称、别名、说明建立本地 FTS 索引，以 BM25 排序；另对去重后的定义卡使用本地 Qwen3-Embedding-0.6B 批量编码，做余弦 top-k。两个通道取并集，再用 RRF 之类的排名融合做候选排序。融合分数只决定检查次序，不是同义概率。公式符号、编码和单位保留单独的精确通道。
4. **中文检索单独验证。** SQLite FTS5 提供 BM25，但默认分词和 `trigram` 对短中文词各有边界。原型先建立可复现的 2/3 字 n-gram 检索列，保留原文；与分词版、精确名称版分别测 Recall@K，不能直接把“加了 BM25”当作中文召回已解决。索引记录分词器和规范化版本。[SQLite FTS5 文档](https://www.sqlite.org/fts5.html)
5. **控制向量规模。** 只给去重后的语义卡编码，不给百万条原始行一律编码。Qwen3-Embedding-0.6B 的 1024 维 float32 向量仅原始数组在 10 万卡时就约 391 MiB、100 万卡约 3.81 GiB，尚未计模型和索引。卡片数在可配置上限内时，复用现有批量编码和精确余弦；超过上限时按范围分区、分批或启用另行验证的本地近邻索引。若只编码一部分，必须报告哪些卡未入索引及该通道的召回范围，不能静默把词法候选当作全量向量检索。[Qwen3-Embedding-0.6B 模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)

索引建成后也不对每张卡逐一发起检索。程序先按表角色、业务范围、单位、公式形态、名称频次和是否已有关系形成统计分层；在每层选高频代表、稀有定义、冲突记录、待查卡与尚未覆盖的种子，给各层保底名额。一个种子从各通道取有界 top-k，并为所有未被查询的卡留下可枚举范围。相互重叠的候选邻域只合并调度名额，不通过相似边合并记录身份。这样能控制检索次数，也使长尾遗漏能在报告中显现；不能宣称未查询长尾已被覆盖。

BM25、向量与规则解决不同问题：规则给出可执行的记录连接，词法检索找相同/相近术语，向量检索补表达差异。实体匹配实践也将廉价候选筛选与较昂贵的判别分开；这里借用任务分解，不借用其指标作为本体质量证据。[Magellan 项目说明](https://pages.cs.wisc.edu/~anhai/projects/magellan/about.html)

## 5. 选哪些记录进入同一个包

每个包先固定任务和种子：一条候选规则、一个定义记录或一个已有概念的未决问题。程序只沿**已验证**的关联规则取确定性跨表记录；词法/向量相似边仅用于寻找待比较定义，不用于图连通分量的传递合并。尚无可执行规则时，可以把两条疑似有关的定义放进概念包共同判断，但包内必须标为 `candidate_only`，不能伪装成已验证的记录连接。关联目标多时保留实际多义；不会随机挑一个目标。

在同一任务内，按以下顺序占用预算：

1. 必需证据：源/目标字段说明、规则与验证计数、目标定义、已知条件和原文出处。
2. 1—2 组目标唯一的正例；若规则分多个条件分支，每支至少一例，装不下则拆包。
3. 一条缺目标、一条目标多义或条件外的反例；概念任务还要选同名不同单位/口径的对照例。
4. 剩余名额覆盖不同业务域、版本、单位、公式形态和低频名称。先用确定性的分层与“新增覆盖项/字节”贪心选择；候选仍过于相似时再用 MMR 降低重复。跨包调度也按新增覆盖和预计字节/调用成本排序，并给未覆盖的小表及稀有层保底份额，避免全局预算被少数高频簇耗尽。MMR 只在已限定的候选池内排序，不能补回此前漏召回的记录。[MMR 原论文](https://aclanthology.org/X98-1025/)

每条记录只带当前任务需要的字段，保留指向完整原文的路径。长字段可作有界展示，但必须标明截断；条件、否定、单位或反例放不下时拆成独立包或保留未决，不能悄悄删掉。单包限制按**完整请求的 UTF-8 字节数**计算，包含系统提示、schema、core 摘要与记录，不只统计 CSV 片段。长上下文还可能让模型忽略中间证据，所以不以增大上下文代替选例。[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)

建议产物 `evidence_bundles.yaml` 中每包至少包含：

```yaml
bundle_id: hash(snapshot, task_kind, seed_ids, selected_record_ids, rule_versions, retrieval_version)
task_kind: concept_induction | relation_meaning | scope_conflict
seed_ids: []
scope: {known: {}, unknown_fields: []}
records: [{record_id: ..., table: ..., fields: {}, evidence_ids: []}]
validated_edges: [{rule_id: ..., source: ..., target: ..., check_id: ...}]
retrieval: [{candidate_id: ..., channels: [exact, bm25, vector], ranks: {}, status: candidate_only}]
examples: {positive: [], contrastive: [], ambiguous: [], missing: []}
coverage: {source_rows: 0, matched_rows: 0, semantic_signatures: 0, sampled_signatures: 0, omitted_groups: []}
size: {request_bytes: 0, limit_bytes: 0, truncated_fields: []}
status: ready | over_budget | unresolved
```

`bundle_id` 只标识证据包；模型响应缓存还需包含 core 哈希、提示词、模型与输出 schema 版本。当前 `record_id` 含整个输入快照哈希和行号，任一文件变化都可能改变大量 ID。因此路线 2 只承诺同快照的确定性复用；新快照将旧包、索引和模型结论全部失效并重新验证规则。跨快照的局部重用需要另建稳定来源身份和依赖图，归路线 3 研究，不能仅靠本次包哈希推断安全性。

## 6. 增量抽取与预算

直接映射继续覆盖所有源列。当前“每表一个语义单元”保留作初始化；接着用关联规则单元和概念归纳单元组成优先队列，按尚未覆盖的语义组、不同范围、冲突和潜在新概念分配配额。一个包可引用多张表，但 delta 只能修改包中声明的来源和对象；程序验证来源、类型约束、规则适用范围与冲突后再原子合并。Judge 复核不能替代程序检查。表级 `max_repairs` 和新的组调度轮次分开计数，仍受共享 `llm.max_calls` 约束。

**两类输出不能共用现有 `RelationPlan`。** 关系语义包输出关系类型/方向/条件候选及其记录级展开规则。概念归纳包输出候选业务概念和 `record→concept` 对齐：原记录 ID、概念 ID、根类型（五类之一）、`exact/narrower/related/unresolved` 判定、适用范围、单位/口径、证据与冲突。概念是带身份的业务语义对象；只有确有类级定义时才另提派生 `ObjectType`，不能再按每张表生一个同名类。对齐是来源映射，不新增一级业务关系；同名、多义和跨范围候选可并列为未决，不用相似度自动做传递合并。

当前 `BuildPlan` 只有每表一个 `TablePlan.object_type`、`DerivedType` 和 `RelationPlan`，尚无记录到概念的对齐契约。实施时应增加独立的概念/对齐 delta、YAML 产物及校验：概念 ID 不能与现有对象冲突，根类型符合内部模型，每条对齐引用真实记录和字段，定义/单位/口径/范围的冲突不能被 `exact` 覆盖；一个记录有多个候选时保留歧义。浏览页面需能从概念追溯原记录及相反证据。只生成词汇表或关系计划而没有这份记录映射，不算完成实例驱动的本体归纳。

概念 delta 的最小结构如下；尖括号是字段占位，不预设实际业务内容。模型只提出候选，程序校验后才写入最终 `objects/` 与 `alignments/`：

```yaml
concepts:
  - id: "<概念ID>"
    root_type: "<五类根之一>"
    label: "<候选名称>"
    definition: "<有来源的定义>"
    evidence_ids: ["<字段证据ID>"]
record_alignments:
  - record_id: "<快照内记录ID>"
    concept_id: "<概念ID>"
    mapping_kind: "<exact|narrower|related|unresolved>"
    scope: {}
    supporting_evidence_ids: ["<原记录字段证据ID>"]
    contradicting_evidence_ids: []
    decision: proposed
```

LLM 输出应区分 `accepted_delta_candidate`、`no_change` 和 `unresolved`，并给出每个新概念/关系的证据 ID、原文片段与范围。没有足够证据时不能为了增加本体节点强制抽取。百万行扫描不导致百万次 LLM 调用；调用数由语义组数、每组尝试次数和全局上限控制。若不同定义几乎条条独有，预算会先耗尽，报告剩余组及来源范围。

检索缓存以快照、字段角色规则、分词器、向量模型哈希、文本卡版本和查询配置为键。已验证规则的结果另以规则版本和快照为键；构建出新 core 后，模型判断缓存需重新检查 core 哈希。新快照不沿用这些缓存。所有阶段保留 `attempted/selected/checked/accepted/unresolved/skipped`，并给出跳过原因。企业 MCP 继续为可选补充，不参与本地实例检索的正确性前提。

## 7. 方案对照与实验

| 实验 | 组包方式 | 用来回答的问题 |
| --- | --- | --- |
| IB0 | 当前按表、前几行和少量精确关联 | 固定基线，定位漏掉的长尾和跨表信息。 |
| IB1 | 规则连接 + 固定哈希的分层正反例，无语义检索 | 仅改跨表组包与基本选例能改善多少。 |
| IB2 | IB1 + 中文词法/BM25 | 名称、别名和公式词项的候选召回增量。 |
| IB3 | IB2 + 本地向量 + 排名融合 | 向量对不同表述的增量，以及误召回和编码成本。 |
| IB4 | 与 IB3 同样的召回，改用覆盖贪心/MMR 选例 | 同一输入预算下是否少重复、少漏条件和反例。 |

同一实验固定输入快照、模型、提示词、单包字节上限和总调用预算，使用独立运行目录。召回分五层报告：原始 Gold 定义行是否入卡、Gold 问题是否被选为检索种子、硬筛是否保留正确候选、已查询种子的各通道条件 Recall@K，以及**以全部 Gold 对为分母**的端到端候选召回。未入卡、未查询、被硬筛排除的 Gold 对均算漏召回。另比较规则验证的唯一/缺失/多义、语义组覆盖、证据支持、错误合并、未决数、token、耗时和磁盘。按“有共同编码/只有别名/只有定义相似/条件分支/同名异义/完全无关”分层，包含留出的长尾。合成数据可检查工程路径；真实业务概念质量须有独立 Gold 或审查，未评估部分写 `unjudged`。任何检索分数、Judge 通过或本体节点数都不能充当语义正确率。

先做 IB1，再做 IB2；只有词法确实漏掉有价值的表达差异，才用本地 Qwen3 做 IB3。IB1—IB3 保持相同的固定哈希分层选例，IB4 才切换到覆盖贪心/MMR；正式方案可采用验证后更有效的选例器。RRF 用排名合并不同检索器的输出，初始常数可参考原论文，但应以本项目的留出集调参，不把融合分数当概率。[RRF 原论文](https://research.google/pubs/reciprocal-rank-fusion-outperforms-condorcet-and-individual-rank-learning-methods/) 全库做两两相似的代表集算法有二次方成本，本原型只在有界候选池内做多样性选择。[apricot 论文](https://jmlr.org/papers/v21/19-467.html)

目标 Windows 离线包目前没有 Qwen 模型文件及其单独依赖；IB3 必须先通过 Python 3.14.7 x64 CPU 上的离线安装、模型哈希、加载、批量编码和 top-k 烟测。缺少兼容依赖时保留 IB2 词法路径，标记 IB3 `not_run`，不能把 macOS 上的模型可用性当作 Windows 验收。[离线运行边界](DATAHUB_OFFLINE.md)

## 8. 实施顺序与当前边界

1. 在数据机先用冻结的当前代码、原始输入、配置、模型和提示词重跑 IB0，放入独立目录，保留失败、跳过和未判定组。旧产物只供历史参照；若取不到原始输入或无法重跑，只做合成工程回归，不声称真实质量提升。
2. 实现关联发现 Agent 的受限规则 YAML、只读工具及完整输入验证；先支持精确键、显式别名、限定的规范化与 selector/作用域。规则未通过验证仍可作为候选。
3. 实现记录语义卡、去重与中文词法索引，建立两类组包任务和分层选例；输出组包及覆盖，不调用 LLM 也能检查。
4. 增加概念对象与 `record→concept` 对齐契约，把两类证据包接到各自的增量 delta/Judge/程序复验，先做 IB1/IB2。再按召回缺口加入本地向量和排名融合，比较 IB3/IB4。
5. 用相同输入和预算重跑，分别判定“候选找得更全”“包内证据更有用”“本体关系确实更准”，不把前两项替代第三项。

代码要求保持简洁：复用现有 DuckDB、SQLite、YAML、AgentScope 和本地 embedding 边界；检索器、组包器、规则验证器用小接口连接，不引入 Docker 或通用多 Agent 平台。
