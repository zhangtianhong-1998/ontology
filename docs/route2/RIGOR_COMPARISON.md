# RIGOR 对照与本轮改造

本文中的代码、配置路径及命令均以仓库的 `route2/` 目录为基准；文档链接可直接点击。

本轮目标：补齐增量构建流程，使用框架的 ReAct Agent 检索企业知识，并提供结果浏览界面。代码仍放在 `code/ontology_r2`，保持普通函数、小型数据模型和单个检索 Agent，不直接修改上游仓库。

## 1. 源码核对

核对版本为 RIGOR `623eedf3e68b3774f36d20215caff4319a0b988a`。依据是其 [app.py](https://github.com/NadeenAhmad/RIGOR/blob/623eedf3e68b3774f36d20215caff4319a0b988a/app.py)，不把实现名称或论文指标当作本项目的正确性证明。

| 原版实现位置 | 旧版路线2的差异 | 本轮处理 |
|---|---|---|
| `direct_mapping_graph_for_table`，483 行起 | 没有独立直接映射；LLM 漏掉的表、字段可能不进入结果 | 先建立所有表、字段、原始类型和声明约束的确定性映射；语义增量失败时仍保存 |
| `traverse_schema_fk_order`，366 行起 | 整库一次性规划，没有处理次序 | 声明外键的目标表优先；无外键按稳定表名排序，循环依赖单独记录 |
| 主循环 1472—1493 行 | 缺少随本体增长更新的上下文 | 每个表形成工作单元，带当前表完整证据、表目录、已有 core 和版本哈希 |
| Gen / Judge，943、1032 行起 | 一次生成、一次整体修订；Judge 不能提供修正增量 | 每个单元生成 delta，Judge 可接受、拒绝或返回 corrected_delta；错误反馈给下一次生成 |
| 主循环 1553—1590 行 | 没有候选合并及逐步回滚记录 | 先在副本中合并并验证，全部通过后替换 core；失败保留旧 core 和原因 |
| 最终校验 1607 行起 | 主要检查实例引用，未检查全字段覆盖 | 最终同时检查直接映射覆盖、完整计划及实例证据；分别报告结构和语义状态 |
| 文档及外部模型检索 | 企业 MCP 用手写固定循环，外部参考已单独对齐 | 企业检索改为 AgentScope 原生 ReAct；外部参考继续保留独立出处和内部术语映射 |
| seed core，1429 行起 | 只有用户的一级 YAML 模型 | 保留内部根模型作为起点；尚不导入历史 OWL 或跨运行 core，避免把失效证据直接沿用 |
| core 检索，864、1481 行起 | 没有随增量更新的 core 检索 | 保留全部类型定义和表类型目录，按当前表及已知关系选择 core 邻域；不引入 FAISS，选择范围及完整 core 哈希明确记录 |

保留有意差异：不按 `id` / `_id` 字段名伪造声明键；不自动丢弃 `s_` 开头字段；不把 SQL UNIQUE 转成“必须有值”；不静默截断文档；不要求 OWL/Manchester。外键声明、样本关联和业务关系分开记录。直接映射只保证输入覆盖，不证明业务分类正确。

原版 property 的 domain/range 约束在本项目中由每个关系计划的源表、目标表及对应对象类型承担；同一个一级关系允许用于不同类型对。SQL 原始类型、非空标志和约束另存于直接映射，不把它们冒充已经对所有记录验证过的业务公理。

## 2. 增量构建

1. 导入 YAML / CSV，保存元数据图、统计和完整直接映射。默认表对象为 `GeneralObject`，状态标为 `source_mapping_only`。
2. 按声明依赖确定顺序。每个工作单元包含当前表的注释、字段、约束、统计、有限样本及相关声明目标；表目录用于定位其他表。
3. 提供当前 core，企业 Agent 输出有出处的知识增量；外部模型单独召回和对齐。已有 core 只用于复用和一致性检查，不当作新的业务证据。
4. 生成当前单元的 delta，只允许修改当前表映射、增加该表发出的关系及有依据的派生类型。不得删除直接映射，不得借当前单元覆盖另一表已接受的定义。
5. 合并到临时副本，校验根类型、父类型、字段、出处及 ID 冲突；Judge 复核后，修正增量再次经过相同程序校验。拒绝、输出格式错误、预算耗尽均保留原 core。
6. 每步保存输入 core 哈希、尝试、delta、Judge、校验错误、输出 core 哈希。最后执行全局校验及批量记录关联。

单元失败后仍导出直接映射、成功增量及未完成单元，运行标记 `partial`。跨快照身份合并、删除旧事实和复杂本体公理仍属路线3及后续研究；本轮“增量”指单次构建中的累积合并。

## 3. ReAct 企业知识检索

本地已固定的 AgentScope 2.0.8 使用统一的 `Agent` 类和 `ReActConfig`，旧版类名 `ReActAgent` 在此版本中不存在。采用该框架的真实 reasoning / acting 循环；模型直接选择注册工具，主程序只约束权限、预算及结果校验。

- 只注册 `search_documents`、`read_document` 两个 MCP 只读适配工具。Agent 可自行改写查询、选择文档、再次检索及结束。
- system prompt 限定任务为当前本体工作单元的定义、关系、口径、适用条件、术语对齐或冲突证据；禁止通用行业综述、重复 core 和无来源的建模建议。
- 每条 claim 包含原文摘录、文档 ID、适用范围、对应的源证据 ID 和增量用途。程序拒绝未读取文档、伪造摘录、工作单元外的来源引用。条件、版本和反证保留。
- 默认 3 个 ReAct 迭代，可配置到 5；另允许 1 次结构化收尾。模型调用、MCP 调用、文档数量、单文档字节数和总上下文均有上限。超过预算不静默裁剪证据。
- 一次模型决策计作一次迭代，搜索、读取与收尾可分别占一轮；不声称“3 轮”必然对应 3 次搜索。需要二次查询时可配置为 5 轮，由 Agent 自行选择次序。
- 无相关知识输出空 claims；工具失败、没有命中和预算耗尽分开报告。只有通过校验的 claims 进入生成器，其余材料保留在检索记录中。
- 模拟模式也运行同一个原生 Agent 和真实 stdio MCP，仅模型响应采用脚本夹具。真实模型仍由用户的 `.env` 配置。

## 4. 结果可视化

每次构建生成本地 `viewer.html`，无需云服务或前端安装。展示本体类型、实例关联、元数据图、证据详情、未决项和增量步骤；支持搜索、视图切换、缩放及点击节点/关系查看出处。

可视化从 SQLite 结果中读取受限预览，并明确显示总量和预览量；不把百万记录一次性装进浏览器。未决关系与已接受关系分别展示。页面不把“运行完成”写成“语义正确”。所有源文本作为文本渲染，页面不向外部服务请求数据。
