# 已审见证的执行成本审查

归档说明：下文是 v8 运行期间形成的性能核查记录。v8 现已结束；优化补丁及结束后的新旧执行器对照尚未应用或执行，本发布分支保持原实验代码。

日期：2026-09-28。范围：关系实例执行阶段；零 LLM 调用。

当前实现对每个带 `witnessed_pairs` 的关系计划重新扫描来源表，再按记录 ID 筛选。这个问题增加本地执行成本，不会自动扩大关系的语义适用范围。433,645 行表的单次筛选实测约 1.61 秒，目前没有据此中断全量 v8 的必要。本轮只补充文档，生产代码和配置保持冻结；优化留待实验结束后单独做零 LLM 对照。

## 1. 代码证据

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| `route2/code/ontology_r2/relations.py:162`、`:191–195` | 逐计划调用 `data.rows(source_table)`，逐行计算 `record_id`，再检查见证集合 | 来源表有 N 行、该表有 P 个计划时，来源筛选成本约为 O(P×N)，即使每个计划只有少量见证 |
| `route2/code/ontology_r2/storage.py:179–187`、`:208–213` | 全列查询、按行号排序、分批转 Python 字典；记录 ID 根据键、行号、快照计算哈希 | 分批读取控制内存，但没有减少扫描和逐行哈希次数 |
| `route2/code/ontology_r2/relations.py:193–203` | 非见证行在 `max_relation_records` 检查之前跳过 | 记录预算限制已审记录的处理量，不限制物理扫描量 |
| `route2/code/ontology_r2/relations.py:149–152` | 进度总数使用见证来源记录数 | 进度数字不能反映后台全表扫描成本 |

非 `identity` 转换还会在 `relations.py:169–180` 物化匹配结果，然后执行上述来源筛选。这次基准没有测量转换物化、目标匹配、结果写入和导出，因此不能将下面的数字视为完整执行耗时。

## 2. 独立实测

将已结束的 `route2/runs/association-rebuild-packets-v6-native-20260928/work/sources.duckdb` 复制到独立临时目录。只测其中 `fruit_market.fruit_param_ref_rule` 对应的 `src_19`：433,645 行、14 列（含内部行号）。使用单线程、512 MB 内存限制，选第 1 行和第 216,822 行作为两个见证。计时脚本调用当前 `Dataset.rows()` 和 `Dataset.record_id()`，执行与生产筛选相同的循环。

| 测量项 | 结果 |
| --- | ---: |
| 全表读取、计算记录 ID、筛选两个见证，一次完整扫描 | 1.608478 秒 |
| 实际扫描 / 非见证 / 命中 | 433,645 / 433,643 / 2 行 |
| 无行号索引，查询两行并复核记录 ID，30 次平均 | 10.272 毫秒 |
| 在临时副本建立行号索引，一次 | 35.577 毫秒 |
| 有行号索引，查询两行并复核记录 ID，30 次平均 | 0.647 毫秒 |

另以只读方式查询已停止 v7 的 `work/semantic_cards.sqlite`，两个见证均可从 `card_sources` 找到。第一次查询 2.204 毫秒，重复查询平均约 0.005 毫秒。SQLite 查询计划确认先走 `card_sources_record(record_id, card_id)`，再走 `cards` 主键索引；独立 DuckDB 副本的执行计划确认行号查询使用索引。

临时副本已删除；没有连接或修改正在运行的 v8 数据库，也没有重跑预处理。以上是一张表的一次全扫描与短查询对照，不是多次端到端性能实验，缓存和机器负载会影响结果。

按本次单表测量线性估算，100 个这样的计划约增加 161 秒来源筛选；1,000 个约增加 26.8 分钟。实际全量开销取决于最终接受的计划数、各来源表大小及转换方式，目前不能据此认定 v8 会出现小时级阻塞。

## 3. 后续最小方案

保留当前关系计划契约，先优化已审见证的来源取数：

1. 从已接受计划的证据建立小型定位表：`(snapshot_id, table, record_id) → row_number`。`group_incremental.py:372–380` 写入的引用证据已有这些字段。只接受行号完整、表和快照一致、定位无冲突的条目。
2. 证据没有行号时，查询现有 `card_sources_record` 索引，再核对 `cards.snapshot_id` 和 `cards.table_name`。该索引有输入上限，不能假设覆盖所有记录。
3. 仍缺定位时，汇总该来源表所有计划所需的记录 ID，最多扫描该表一次，只保存需要的 ID 与行号映射，并缓存未找到的 ID。这样即使无法复用卡片索引，也不会每个计划重复扫描。
4. 为来源表的内部 `__r2_row` 最多建一次索引，以有界批次取指定行。现有 `Dataset.lookup()` 只允许声明列，不能直接传内部行号；增加一个专门的行号读取方法即可。
5. 对每条取回记录重新计算 `record_id`，同时校验表和快照；定位信息只用于加速，不能作为身份成立的依据。按原始行号排序后，继续执行现有 selector、scope、transform、目标唯一性和见证目标 ID 检查。

定位失败、行号冲突、未知 ID 要明确报告，不能改为执行整列关系，也不能把目标多义当作成功。非 `identity` 转换的物化成本另行计时；如果后续缩小来源查询范围，仍须保留完整目标键的歧义核验。

## 4. 覆盖统计与回归要求

优化只改变取数路径，不增加可输出关系的记录集合。计划顺序、计划内来源行顺序、全局 `max_relation_records` 扣减顺序和见证集合去重方式保持一致。

| 回归项 | 验证要求 |
| --- | --- |
| 输出与证据等价 | 同一快照、同一计划集下，关系事实、目标 ID、引用证据、selector 真/假/未知结果与原执行器一致；缺目标、多义目标仍未决 |
| 已审范围 | 同值但未被审查的来源行不能输出关系；不同计划的条件和见证不能串用 |
| 快照变化 | 快照不符在取数、写结果前拒绝；跨表定位不能借用 |
| 伪造行号 | 行号指向另一条记录时，ID 复核失败；不能输出错误关系，可经一次来源索引查回真正记录 |
| 未知或冲突 ID | 明确报告未定位/定位冲突；不扩大到全列执行，不重复全表重试 |
| 预算 | 预算为 0、恰好够用、跨计划耗尽及最后一个见证位于表尾时，已处理和未处理数量与原路径一致 |
| 覆盖统计 | 完整执行时保留 `total_source_records`、`witnessed_source_records`、`examined`、`outside_witness` 的含义。预算中途耗尽时，原 `outside_witness` 仅计停止前遇到的非见证行，不能直接替换为全表行数减见证数；必要时按停止行号做确定性的计数查询 |
| 物理扫描统计 | 单独记录实际扫描/读取行数、定位命中与来源索引回退次数，避免把逻辑未审范围误称为实际扫描量 |
| 索引缺失 | 卡片索引缺少记录、没有索引文件、多个计划共用同一来源表时，回退扫描每表至多一次；缓存不会跨快照复用 |
| 转换与作用域 | 条件分支、scope、大小写/别名转换和重复目标检查保持原结果；直取见证不能绕过原核验 |

全量 v8 结束后，可在其独立数据副本上复用已接受计划做新旧执行器对照。这个对照不需要重新请求 LLM，也不需要因保守未决重新进行语义抽取。
