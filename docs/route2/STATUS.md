# 路线2当前实现状态

以下状态对应仓库 `route2/` 的代码和合成数据测试。用户提供过数据机运行统计，但仓库没有真实业务数据，本文未独立复现该结果；Windows 真机运行也尚未验证。`complete` 只表示本次配置下执行与结构校验完成，不表示隐含业务关系已全部发现。

2026-09-25 的失败原因、三层目标模型和整改顺序见[抽取失败复盘](FAILURE_REVIEW_20260925.md)。

本轮实现与复跑结果见[优化与验证记录](OPTIMIZATION_AND_VALIDATION_20260925.md)。真实配置现采用 `source_mapping_only`：逐表阶段只保留物理映射和源记录类型；LLM 调用限于可选的关联 Agent 与选中的跨表记录包。旧的 `table_semantic` 模式供原有示例和回归使用。

最新前处理和浏览改造见[配置定义与业务事实设计](FACT_CONFIG_ONTOLOGY_DESIGN.md)、[元数据图契约](METADATA_GRAPH_CONTRACT.md)与[可视化说明](VISUALIZATION.md)。输入仍只按**整表启发式**区分定义、配置和事实；明显事实行不进定义卡。定义卡按完整语义内容形成候选调度模式，但同文不同编码仍保留不同记录身份，只有模式代表可作为精确对齐候选。对事实表，只组装实际出现的维度/期间/数值元组；字段级模型判断及原行回查通过时可产生快照内事实观测实例。合成 23 表 1,102,238 行前处理保留 24,780 张定义卡、580 个模式，80 个概念包覆盖其中 80 个模式；无逐行 LLM 调用。当前 `max_concept_bundles: 80`、`max_llm_bundles: 120` 与共享 800 次模型调用上限仍会留下未抽取定义，运行报告明确列出该范围。最新 13 行合成复跑 v10 为 9/9 入选包接受、1 种业务关系、2 个已回查事实实例，但使用了 20 次缓存命中，只有 1 次新增模型调用；整体仍为 `partial`，详见[实验记录](OPTIMIZATION_AND_VALIDATION_20260925.md)。

程序候选发现不会把值重叠直接解释为业务关系。真实配置现用 `full_distinct` 和 50 对候选核验上限；预算外候选写入 `discovery_coverage.yaml`，语义卡、规则和组包各有覆盖报告。正常完成输出时从 `manifest.partial_reasons` 查看未核验、未入卡、未选包等范围；提前异常中止时查看 `manifest.error`。LLM 调用次数由选中组数与全局预算决定，不随记录数逐行调用。

仍未实现标准名到别名、编码变换和复合键的完整规则验证；列角色只是保守过滤。组级概念对象独立于“每表一个基本对象类型”的旧计划，尚未实现同表多类型分派、跨快照稳定身份、异常值分层选样或对概念质量的 Gold 评测。单个组包有字节上限，完整请求还有 LLM 层的 `max_input_bytes` 准入；两者不保证组包覆盖率。早期完整 CLI 合成试验曾把“同一指标的多表属性描述”接受成对象关系；新增防护在重放中移除了该边，但尚未把这类记录正确地对齐为同一概念。用户数据机的“0 个关系类型”问题须在同一输入与配置上重跑；合成测试不能代替真实关系质量评估。合成实验与未测项目见[水果经营实验记录](EXPERIMENT_FRUIT.md)。
