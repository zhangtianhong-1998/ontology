# 水果经营合成数据：路线 2 本机实验

以下为 2026-09-24 的本机检查，仅使用 `route2/scripts/generate_fruit_data.py` 生成的虚构数据。生成器不调用 LLM，也不读取用户真实业务数据。提示词列出的五个域实际合计 22 张表；脚本为满足“23 张表”测试需求，额外添加一张 70 列、无主键的合成导入临时表。数据和运行产物在 Git 忽略的 `route2/local_data/`、`route2/runs/`，不随仓库上传。生成、校验和运行命令见[合成输入说明](../../route2/scripts/FRUIT_FIXTURE.md)。

## 修复后输入 v2

生成器修复了参数 `param_id` 的唯一性与业务作用域，以及维度类 `field_rule` JSON 值必须属于对应维度成员的问题。重新生成 `local_data/fruit_data_v2` 和 `local_data/fruit_smoke_v2`，不复用旧数据。全量验证为 **23 表、1,102,238 行**；其中参数引用规则 433,645 行、维度规则值 216,825 个，可解析数学公式 3,200/16,000 条。小样本仍为 23 表、1,213 行。脚本校验列顺序、主键、无声明外键及预设引用约束；这些只证明合成输入内部一致。重跑时在配置中明确指向 v2 路径，避免误用旧输入。

修复后全量**程序组件**扫描（`runs/fruit-full-components-corrected-20260924`）用时 46.11 秒：976 个字段候选中核验 50 个，109 个全空/审计/敏感字段退出非声明候选；规则状态为 8 个 `checked_technical`、1 个 `observed_subset`、51 个未决。索引 49,139 张卡，另有 784,841 行因卡片配额未入卡；形成 12 个概念包和 4 个关系包。`checked_technical` 只表示本次输入的物理匹配经核验，不能算业务关系；扫描百万行也不表示百万行已完成语义抽取。

修复后**小样本组级在线试验**（`runs/fruit-volc-groups-corrected-20260924`）在 23 表、1,213 行上得到 1,017 个字段候选，核验 50 个；规则状态为 10 个 `checked_technical`、3 个 `observed_subset`、47 个未决。索引 1,072 张卡，形成 12 个概念包和 5 个关系包，从 17 包中选 6 包。经 AgentScope 向火山引擎 `deepseek-v4-flash` 发起 10 次新的非流式调用，服务端报告 48,085 token，10 次均以 `tool_calls` 结束。自动检查接受 3 个快照内概念（指标、度量、维度）及 12 条记录对齐；3 个关系包均未决，**0 个对象关系类型**，另有 11 包未尝试。维度成员的 `contains` 提议被复核拒绝，说明引用键匹配没有被直接升级为业务关系；但这些概念与对齐尚无独立语义 Gold，接受数不是准确率。

同一 v2 小样本、同一模型参数的独立重跑（`runs/fruit-volc-groups-corrected-replay`）虽然目录名含 `replay`，由于缓存目录参与缓存键，实际是 **7 次新火山引擎调用、29,878 token、0 次缓存命中**。这次产生 0 个概念，却接受了 1 条 `contains`：规则方向为 `fruit_dim_member → fruit_dim_definition`，文字含义却是“维度包含成员”，属于方向误判。随后代码增加“子记录指向父记录时不得生成 `contains`”的保守检查；以第一次 v2 在线试验的响应在最终代码上重放（`runs/fruit-volc-groups-final-replay`）为 **0 次新调用、9 次缓存命中**，得到 3 概念、12 对齐、0 关系，6 包中 3 接受、3 未决，11 包未尝试。独立重跑和缓存重放都不能当作语义成功率；组包内候选的模型判断会波动，关系方向和对象身份仍需专门验证与改造。

来源约束重放保留的“销售渠道”维度概念引述一条维度定义、两条成员和一条字段记录；其中定义记录为 `exact` 来源，成员和字段保留较弱的映射类型。两个关系包被复核拒绝，原因涉及把技术键匹配直接当作 `contains` 或 `related_to` 业务关系；还有一个匹配由模型保持未决。共享定义键的同根定义表记录不再自动进入对象关系包，因此**该次重放**接受的对象关系类型为 0。这不能证明合成数据中没有业务关系，只说明这 6 包的有限证据、模型判断和自动检查没有接受它们。

修正前的完整 CLI 运行另接受了一条 `fruit_metric_anchor → fruit_metric_attr` 的 `related_to`。它描述同一 `metric_code` 下的业务锚点与指标公共属性，较像同一指标的两份定义/属性来源；严格定向试验对近似候选曾给出未决。新增的共享定义键防护已在上表重放中移除这条对象关系，但目前只是保守跳过，并未自动产出正确的跨表记录对齐。下一步需验证此类共定义线索的对齐规则和业务对象关系边界。

修正前的诊断曾把规则表记录抽成维度概念，并把物理编码连接表述为 `points_to`；更晚的一次诊断又把同一指标编码的两个定义表当成 `related_to` 对象关系。随后将规则/配置/锚点/日志记录改为上下文卡；同根定义表或锚点/定义表共享定义键时优先作为对齐线索；关系输出必须从同一条已核验正例的两端**非关联键、未截断记录值**逐字引用，不能只靠编码或字段注释；`exact` 对齐遇到截断语义字段会被拒绝，新概念还必须有完整的 `exact` 定义来源。严格组级在线试验重新调用了模型；来源约束重放没有新增调用；完整 CLI 的最新重放则因请求变化新增 2 次调用。

## 可重跑范围与未验证项

仓库提供生成器、验证器和 `config/runtime.fruit.example.yaml`。样例默认关闭企业 MCP、外部本体、实例向量和关联 ReAct Agent，使用非流式请求及 `thinking.type=disabled`；其 `max_llm_bundles: 4` 与上表定向 6 包试验不同，直接运行样例的结果不能逐项复现上表。模型试验的本地输出目录与缓存未提交，报告保留输入规模、调用方式、提示词哈希 `e4aac25e804f7012a9469706e2ae8e51bb186a06331e0fabaf6b060d72fcaf58` 和统计作为核对线索。请用新运行目录复测；只有刻意重放相同响应时才复用缓存。

尚未在最终代码上完成 110 万行的**完整 CLI + LLM** 重跑，也没有真实数据上的候选 Gold Recall@K、概念身份/关系质量判断、IB0—IB4 公平对照、向量通道实测、关联 Agent 的规则质量对照或 Windows 11 / Python 3.14.7 离线验收。百万行程序扫描、少量合成证据包被模型接受与真实本体自动构建质量是三件不同的事。
