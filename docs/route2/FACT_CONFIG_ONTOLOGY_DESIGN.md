# 路线 2：配置定义、业务事实与本体增量

本文描述路线 2 的抽取边界。输入可以只有配置表、只有业务事实表，或两者兼有；水果经营数据仅用于合成实验，不能代表真实库的字段和口径。

## 1. 三层结果与两类输入

| 层 | 输入与输出 | 身份 |
| --- | --- | --- |
| 物理层 | YAML 表列、约束与 CSV；生成表、列、主键、来源、源记录类型及受限的记录预览 | 表/列使用来源位置，记录使用输入快照内 ID |
| 定义层 | 指标、度量、维度、术语及其配置记录；生成带证据的业务类型、关系类型和定义对象 | 名称不能单独定身份；比对定义、公式、单位、适用范围和版本 |
| 观测层 | 某经营对象在地区、期间等坐标下的实际业务值；生成可追溯的业务实例或事实 | 定义 ID + 已观察到的维度成员 + 时间粒度/期间 + 业务对象 + 必需版本；不能枚举所有可能组合 |

目标是把表行分为 `definition`（定义对象）、`reference`（配置引用）、`observation`（业务事实）、`technical`（审计/导入等）和 `uncertain`。分类必须给出表/列/行依据；同一张表可能混合多种记录。`reference` 行用于发现关系，不因为有名称列就成为新业务类型。审计时间、流水号、空列保留为物理属性或过滤条件，通常不进入 LLM 语义证据。无法可靠区分时保留 `uncertain`，不能为了提高节点数强制升格。

当前原型只做**表级行用途启发式**：`definition_data`、`configuration_data`、`business_fact`、`unresolved`。明显事实表被排除在定义卡之外；程序对这类表按已观察到的维度、期间和数值列形成去重候选。可选的 `fact_type_binding.py` 再按**数值字段**召回已接受的 Metric/Measure 类型，每字段至多一次 LLM 判定，逐字核对列注释、完整来源定义、单位与适用范围，然后回查每个候选的原始行，才生成快照内观测实例。坐标列遗漏、同坐标多值、来源行不完整或类型歧义均不实例化。已证实等价的一组来源类型可共用一个快照内规范类型；没有完成证据核验的同名类型仍视为多义。混合表按 `unresolved` 保留；这并不声称逐行准确分类或跨快照业务身份稳定。

**Metric 与 Measure 的边界。** Metric 必须有可引用的业务目标、经营语境或业务口径；Measure 是纯数值聚合、过滤或基础定量度量。表名中的 `metric/measure` 仅是召回线索。类级 Metric/Measure 决策须输出对应分类依据，并逐字引用完整定义记录中的语义字段；程序检查引用与分类枚举相容，复核仍不能代替业务专家判定。利润指标可以依赖收入、成本度量，但同名或数值相等不证明这种依赖。

## 2. 避免笛卡尔组合与重复抽取

1. 对每列统计非空、不同值数和频次；基于列说明、类型及观察值挑选少量候选角色：定义键、引用键、维度坐标、时间、数值、审计。只对有依据的候选列组合计算 `count(distinct tuple)`、唯一性、重复倍数、空元组比例及反例；限制组合宽度和数量，不穷举全部列的幂集。
2. 对配置定义行，保留包含编码和引用字段的**原始卡片身份**，另以完整的名称、别名、说明、公式、单位和适用范围形成**语义内容模式**。不同编码可以落在同一模式；模式只用于选代表组包及复用分类判断，不自动合并业务对象身份。SQLite `card_sources` 保留入卡行与出现次数，最终概念映射仍只物化已判定的代表行；其他同模式编码记录保持未对齐，须报告数量。任何语义字段预览截断时独立成模式。相近名称、BM25 或向量结果只召回候选，不能据此跳过或合并。
3. 对业务事实行，先按实际观察到的维度、期间和数值列元组去重，不生成地区 × 时间 × 产品的全部理论组合。`fact_observations.py` 在 DuckDB 中对每个入选数值列做全输入精确分组，导出有限个 `candidate_only` 候选、重复次数、来源行号上下界和同坐标多值歧义；行号上下界不是该组的精确行号列表。数值列、维度列和候选条数均有配置上限，超限和未扫字段明确写入覆盖报告。定义/配置/未决表也保留在报告中。`fact_type_binding.py` 仅对已有、证据完整的业务类型做字段级匹配，模型必须完整复述类型定义与一条原始来源定义；超长、缺失或相互冲突的来源定义会使该类型退出绑定。实例化前，程序按坐标和值重新读取全部来源行，核对数量、边界、快照以及未选入坐标的其他非技术字段是否在合并行之间发生变化；发现变化、超过行上限或仍有未证实等价的多义类型便保留候选。当前仅能生成有明确列注释、单位和唯一规范类型对应的观测实例；单行数据中遗漏的维度仍无法被这种组内变异检查发现，未实现一般别名关系、多表 JOIN 或维度成员对象关系。
4. 目标是对已接受类型与关系使用同一快照内的规范签名比较。完全相同的类型定义、适用范围、单位和端点关系才可跳过再次请求 LLM；不同证据仍须增加来源映射。当前实现模式窗口、组包前完整证据签名与同规则签名去重，**没有**实现对已接受本体的跨运行增量复用。`max_pattern_seed_pool` 和 `seed_window_index` 分页调度模式；实际窗口宽度至多为 `max_concept_bundles`，确保页内未处理的模式不会被下一页跳过。单次构建只运行所选页，换页不会继承前一运行的已接受类型，也不能把多页结果当作一个已合并本体。任何语义字段被截断、缺少口径或作用域不明时不得作为安全去重依据。

专家提出的“先列 `DISTINCT`，再反向索引回源行”作为关联候选路径：先在候选列/列组的不同值上找相交或可解释的转换，再按值取回代表正例、缺失和多义源行，形成规则证据包。这样避免全表两两行比较。原值相同只代表技术候选，别名/标准名映射必须有受控变换和留出验证，不能用一个正例推广整列。

## 3. 组包与增量抽取

配置定义包以一条完整定义为种子，可附同名异义、相近定义及其反例；**找不到第二条相似记录，也不应丢弃有完整定义的独特种子**。关系包以经全输入验证的引用规则为种子，取回源/目标实际记录和条件内外的例子。事实包只在新模式出现时取少量观察值，维度成员和期间以坐标身份进入，而不是派生类名。

组包按来源角色、业务根类、表、语义签名和新增覆盖量分配预算。对每类分别报告：全输入行数、可入卡行数、不同签名、候选种子、入选包、LLM 已处理包、接受类型/关系、未尝试/未决及原因。`max_cards`、`max_concept_bundles`、`max_llm_bundles` 是不同闸门；扫描一百万行不等于逐行调用 LLM，也不等于抽取完所有不同定义。

LLM 输出须分开：`source_record_type` 由表结构确定；`business_type` 由定义行支持；`business_instance`/事实由实际观察行和类型绑定支持；`business_relation_type` 由引用/公式语义支持；实例关系需要见证行和条件。当前代码实现物理源行类型、有限来源定义的业务类型、见证关系、从**两个已接受且原文完整的特化定义**归纳共同上位类型，以及保守的数值字段类型绑定。上位类型阶段需要模型提出候选、程序核验共同语义和去特化模板；不会自动泛化子类对象关系。事实绑定只面向已接受 Metric/Measure 的单表观测值；别名值规则、跨表事实 JOIN 和同表多业务类型分派仍待完成，不能把技术图的连通性称为业务语义质量。

**已接受类型的等价核验先于事实绑定。** `type_equivalence.py/type_equivalence_stage.py` 仅用同根、同名、同单位、同适用范围召回候选，不把这些条件当作等价证明。每一对都把两端完整来源说明与公式交给模型；模型须逐字引述两端原文。程序只接受完整说明在规范化空白、标点后相同，且完整公式相同（可忽略赋值号左侧名称）的类型；文字改写即便算式相同也保留分立，因为固定的限定词词表无法穷尽“直营/加盟”等业务范围差别。一个同名组必须**所有两两组合**均接受，才能建立同一输入快照内的 `canonical_type_id`；少核一对、公式冲突、原文不完整、模型未决或反对时，该组不归并。被归并的原始类型与来源证据继续保留，规范 ID 仅让事实字段消除已经证实的多义，不把定义记录的编码或观测坐标合并。此处的程序校验及模型判定只是有据可查的原型决策，尚无独立业务 Gold 证明其语义正确。

配置关系与定义记录直接关系分开：`configuration_relations.py` 只从同一配置表的两条已核验原值引用中形成双编码候选，并在完整输入中分别核实目标定义唯一、已精确对齐业务类型；`configuration_relation_stage.py` 只有在配置行的完整关系文本明确点名两端和方向，且两端完整定义引文核对通过后，才生成业务关系类型与概念关系。配置行是证据，不是关系端点。当前未覆盖按 `source_type` 选择目标表的单字段多态引用、别名异值转换，以及没有明确方向文字的配置关系。

接受的业务类型会把 exact 定义记录中的名称、说明、公式、单位等列作为 `definition_record_only` 来源属性列出，引用原文并保留源表/列。这些是**定义记录的属性映射**，不是断言每条经营事实都有同样的属性值。对象关系也分别标明技术表关系、业务类型关系及其证据范围。

## 4. 验收实验

固定一份合成输入与独立小型 Gold，至少覆盖：单条独特定义；相同定义的重复配置行；同名不同单位/口径；一个指标引用两个度量；一个度量被两个指标引用；地区与季度形成多个**已观察**事实；别名与标准名异值关联；多态引用、缺目标、多义和技术 ID 碰撞。比较改造前后在相同调用/字节预算下的定义入卡率、种子覆盖率、类型与关系的召回及误接收、实际观测实例数、未处理范围和运行成本。另用 23 表合成输入验证规模与 UI，不以合成工程通过率代替真实业务准确率。

代码要求简洁：继续使用 DuckDB/SQLite 的分组和倒排、受限的现有组包器与一个共享 LLM 接口；不新增逐行 Agent，也不引入 Docker 运行依赖。

每次构建都会写出 `fact_observation_candidates.yaml` 和 `fact_observation_coverage.yaml`。默认开启，可在运行配置的 `fact_observations` 下设置 `enabled`、`max_candidates_per_table`、`max_dimension_columns`、`max_time_columns` 与 `max_value_columns`。关闭时仍写出 `disabled` 覆盖记录。候选上限导致遗漏时，`manifest.yaml` 标为 `partial`；该阶段不调用 LLM，也不把候选计入已接受的本体类型、关系或实例。`type_equivalence` 可配置 `enabled`、`max_pairs`、`max_decisions`、`max_packet_bytes`，产出 `type_equivalence_steps.yaml`、`type_equivalence_assertions.yaml`、`type_equivalence_coverage.yaml`；`ontology.yaml` 保留原类型，并只在完整核验组上附 `canonical_type_id`、`equivalent_type_ids` 和等价断言。可选的 `fact_type_binding` 阶段另写出 `business_fact_field_bindings.yaml`、`business_fact_instances.yaml` 和 `business_fact_binding_coverage.yaml`；实例同时引用原始列元数据、类型定义、等价依据（如适用）和所有匹配来源行的值证据，未实例化的候选及原因单独计数。
