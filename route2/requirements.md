# 路线2：需求与用户故事

本文中的对象、字段、公式和地区等均为假设性例子，不说明真实输入包含这些内容。运行时先检测证据和适用性；没有相应内容就不启用该提取器。目标模型的五类根也不要求输入覆盖全部类别。

## 1. 需要解决的问题

元数据一般足以说明表、列的用途。新增分析聚焦三个产物：

1. 定义对象：一条记录描述什么，如何保留其来源身份和类型依据。
2. 记录关系：具体记录引用或依赖哪些对象，引用来自哪个字段或定义。
3. 关系条件：哪些记录适用，范围来自哪些真实字段或显式规则。

没有显式外键和血缘时，检测输入实际存在的字段引用、文本、公式或上下文；仅使用其中可获得的证据发现候选。只使用实际存在的来源，不要求用户先补齐查询日志或 ETL 系统。

## 3. 功能边界

- 元数据图不要求部署 OpenMetadata/DataHub；当前导出文件足够建立最小图。未来的 catalog 连接器只需转换到 SourceRef 和元数据节点，不改核心算法。
- 不做全字段通用数值画像。只计算关联需要的非空比例、不同值数、候选目标唯一性、包含率、标识格式和选定枚举等；全量统计与样本统计标明范围。
- 不把整张 CSV 发给 LLM。不为每一行启动 Agent。企业 MCP Agent 按有限的源表工作单元运行，不为每条记录创建 Agent。
- 当前代码由 LLM 提出抽取计划，程序检查后执行。下一阶段增加程序候选召回、有限补样与精确验证，LLM 补语义判断。任意稀有模式的完整发现仍不保证，未覆盖组和未处理候选必须报告；导入记录数不等于关系召回率。
- 外部本体与企业文档分两条来源通道。外部模型提供建模参照，企业文档可能提供业务定义；后者也必须检查适用范围，不能天然覆盖源数据。
- 输出包含 ontology、业务定义对象、记录关系、条件、证据和未决项。路线3才增加可复用映射契约、全局身份融合和增量失效处理。

## 4. 非功能与接受要求

原型先验证小样本完整流程，再做 10 万、100 万记录的导入和受预算约束的执行。百万全量语义抽取单列为规模实验，不能由截断运行代替。目标定义与标识建索引，不枚举所有记录对。执行器每次读取 1,000 行，输出默认每片 5,000 项；预算以实际运行配置为准。

接口输出必须稳定可解析；语义结果允许未决。任何“低温度、重复投票、Judge 同意”均不能作为稳定正确的保证。评测应同时报告正确率、召回、未决比例和处理范围。

缺失文档不阻塞有证据的本地关系；MCP 故障与无结果分开。定义不足时不增加 LLM 重试来强迫其给出答案。

US14—US18 为本次新增、尚未实现的要求。算法、数据契约和初始预算见[字段统计与关联发现设计](FIELD_PROFILING_DESIGN.md)，先后顺序见[实现清单](implementation.md)的 P01—P06。
