# 路线1：需求与用户故事

本文中的对象、字段、公式和地区等均为假设性例子，不说明真实输入包含这些内容。运行时先检测证据和适用性；没有相应内容就不启用该提取器。目标模型的五类根也不要求输入覆盖全部类别。

## 1. 范围

保留 RIGOR 的按表迭代、增量本体、生成器和 Judge 角色。输入及输出改为[共同契约](../shared/contracts.md)，使用用户给定的根对象和关系。缺少 FK 时按稳定顺序覆盖所有表；不开展值匹配、记录分析或推测血缘。

1A 与 1B 共享代码、模型、提示词模板和预算。差异仅是外部模型来源及其必要的对齐步骤，调用成本分别计入。一次实验从空的业务 core 开始，只装载固定根模型，不能自动读取以前生成的本体。

## 3. 功能要求

1. 输入归一化：完整限定表名、复合键、原始约束、解析状态与快照哈希。
2. 技术覆盖清单：逐表逐列记录“已处理、未处理、失败”；字段不需要为了提高覆盖率都变成业务属性。
3. 语义生成：以当前表、注释、已声明约束、相关已生成类型及根模型形成上下文。输出类型、关系、属性定义和源映射候选；没有记录证据时不输出具体业务对象。
4. 自动复核：先结构校验，再 Judge 检查语义及依据，再程序检查引用、继承、关系 kind 和冲突。Judge 只能使用同一份证据，不得补造数据。
5. 外部模型：按统一 ExternalCard 适配 RDF 模型和 CDM；先实现单模型试验，支持模型选择开关，禁止一次把四个完整模型塞进上下文。
6. 输出：统一 YAML 和 manifest；source coverage 与业务类型覆盖分开。失败表与成功表都计入报告。

## 4. 非功能要求与边界

- 默认每表一次生成、一次 Judge；无效结果最多两次修复。总调用和 token 上限覆盖生成、Judge、翻译和外部对齐，不允许绕过预算。
- 单表过大时按完整列定义分组，保留键与约束上下文，并做表级整合；超预算就标 partial，不静默截断字段或约束。
- 只保证契约和执行策略可控，不保证仅凭注释得出正确企业语义。输出的业务分类须标明其来源是 `schema_derived` 或模型推断。
- 1A/1B 比较使用同一源文件，不因外部本体丰富就给 1B 更改评价问题或标准答案。
- 首版无数据库直连、图数据库、人工审核界面和生产发布功能。
