数字键、主键列也可能是真实引用：若原始元数据有精确对应的外键声明，允许它通过前述候选门槛，仍须完成全量值核验和业务用途判断。只靠规则自称“已声明”或注释猜测不适用这个例外。当前 23 表没有声明外键，诊断结果不因此改变。

## 已有本体如何减少调用

1. 先尝试完整模板匹配。类定义、公式、单位、参数及字段契约全部成立时直接增加实际绑定，不调用模型。
2. 部分匹配保存“已确认字段”和“未覆盖字段”，并从完整的已接受类型集合召回相容端点。相似度、同词和部分字段匹配都不能单独证明同一性。
3. 若已有“合格率”的独立定义，可以复用其度量端点。新出现的“香蕉”先保留为实际取值和待发现任务；没有来源依据就不创建香蕉类型。
4. 第二轮按旧模板及缺口组成定向任务，使用少量真实代表记录。新的匹配契约仍须重新应用到实际记录，不能把整个候选组直接宣布通过。
5. 已接受的 ID、定义、公式与口径不因修复而改写。旧失败只有在实际代表记录重新匹配、相应缺口得到解决后才标记为已修复；首轮未处理范围继续保留。

对 v9 产物的零模型规划得到 26 个缺口组、52 条实际代表记录，分为 11 组缺端点、9 组字段不覆盖、6 组缺来源定义。涉及的其他候选并未因此获得语义认证。

适用范围也必须由模型明确提出，并在来源中验证为所有见证记录的完整不变值。不能从一条观测记录的地区或年份推导整个类型的适用范围。变量度量槽位逐值核验，不会因为首条记录是“收入”而把后续的“成本”也绑定成收入。

## 实例化的验收要求

本体类型必须具有可检查的来源映射。程序按映射回读数据，重新核验记录身份、模板、字段值、公式及证据，再物化节点和关系。

- 定义或配置实例：某条指标定义、API 配置、看板配置对应的实例。
- 语义成分出现记录：同一来源记录中明确绑定的经营对象、度量或维度，有所属记录与证据。
- 经营观测实例：确有业务数值及坐标的实际记录，例如某地区某期间的利润；沿用事实绑定通道。

三者不能互相冒充。模板、公式和配置关系只按已验证端点生成边，禁止通过两端类型的全部实例做笛卡尔积。缺源记录、缺目标定义、证据冲突或超出范围时输出未决项；没有映射的类型列入未实例化清单。

输出包括 `objects/`、`assertions/`、`ontology_instance_mappings.yaml`、`ontology_instance_coverage.yaml` 和 `ontology_instance_pending.yaml`。有节点不等于已验证计算值：本轮不会为缺少事实来源的配置编造收入、利润数值。

## 预算与运行

当前全量配置为 `route2/config/runtime.fruit-templates.yaml`：

```yaml
llm:
  max_calls: 3000
  request_interval_seconds: 0.2
instance_bundles:
  reserve_calls_for_followup: 600
targeted_repair:
  enabled: true
  max_rounds: 2
  max_tasks_per_round: 80
  max_examples_per_task: 3
  max_calls_per_round: 400
  reserve_calls_for_followup: 300
ontology_instantiation:
  enabled: true
  max_records: 1200000
  max_assertions: 2400000
```

两轮共享 3,000 次预算，首轮最多用到第 2,400 次，第二轮最多额外 400 次且为后续阶段保留 300 次。实际可用量取这些上限的较小值。没有任务、没有语义变化或触及预算时停止定向修复，不为凑足轮数重复请求。

调用在同一运行内串行发送；每次完成或失败后等待至少 0.2 秒再发送下一次，可配置为 0。缓存和 mock 不等待；此设置不是跨进程的服务限流器。

新实验在保存 Git 版本、完成回归和启动预检后独立后台运行。自动保存结果、覆盖范围、退出状态和 HTML；启动后不持续监控，用户通知后再分析。

本轮实验输出目录：`route2/runs/fruit-templates-full-v10-20260929`。启动记录和日志分别保存在 `route2/local_config/fruit_templates_full_v10_launch.json`、`fruit_templates_full_v10.log`。
